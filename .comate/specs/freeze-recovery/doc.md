# 游戏窗口偶发「卡死」：原因分析 + 自动降级 / 自愈 / 诊断增强

## 1. 现象

部分机器在以下时机**整个游戏窗口突然无响应**（不是变慢，是卡住，只能强关）：

- 点开某些游戏内面板/弹窗
- 进入战斗
- 战斗结算/切场景

## 2. 可能原因（按可能性排序）

### 2.1 显卡驱动挂起（最大嫌疑）

启动器默认加 `--ignore-gpu-blacklist`，**无视 Chromium 的显卡驱动黑名单强制开硬件加速**。被官方列入黑名单的驱动本来就不适合做 GPU 合成；而 Flash 在「打开新面板 / 进战斗 / 战斗结算」时会集中新建大量位图与 GPU 纹理，正是最容易把这种驱动压挂的时刻。

- 现有设置里虽然能关（强制启用 GPU），但：
  - 用户不知道什么时候该关；
  - **崩过一次之后没有任何自动降级**，下次照样开，照样卡。
- 这类卡死往往是驱动层面的（TDR），主进程和渲染进程都没机会报错，所以日志里什么都看不到。

### 2.2 变速 hook（`speedhook.dll`）

非 1x 时，会把 DLL 注入到渲染进程 / Flash 插件进程，hook 计时 API。战斗切换时 Flash 会高频调用计时函数，如果 hook 存在竞争，理论上可能死锁。

- 现有代码已经在 **1x 时不注入**（`injectAllChildProcesses` 首行判断），所以 1x 用户不受影响；但长期挂 2x/4x 的人在战斗切换时风险最高。
- 目前没有任何「疑似 hook 导致卡死」的日志，出问题无法定位。

### 2.3 渲染进程 OOM / 崩溃

Flash 长时间运行内存持续增长，战斗资源加载是峰值。触发 OOM 时可能是白屏，也可能表现为长时间卡住。现在**没有任何检测、提示或自动恢复**。

### 2.4 弱机 CPU 抢占

`disable-renderer-backgrounding` + `disable-background-timer-throttling` + `disable-backgrounding` 让后台标签页也不降速。多开 + 弱机时，切到战斗这种 CPU 尖峰场景，前台窗口可能「看起来卡死」（实际是没抢到 CPU）。

## 3. 方案

### 3.1 P0：GPU 崩溃自动降级

监听 `app.on('child-process-gone')`：

- 当 `details.type === 'GPU'` 且 `reason` 是 `crashed` / `oom`：
  - 写 `ERROR` 日志（含 reason / exitCode / 时间）；
  - 把 `config.forceGpu` 置为 `false` 并落盘（**下次启动不再强制开 GPU**）；
  - 记一个 `gpuCrashAt` 时间戳。
- 启动器下次打开时，若存在 `gpuCrashAt`：弹一次提示
  > 「上次运行检测到显卡进程崩溃，已自动关闭『强制启用 GPU』。如果之后画面正常，可以保持关闭；想恢复可以在设置里重新打开。」
  提示后清掉 `gpuCrashAt`（只提示一次）。
- 顺带：`details.type === 'GPU'` 的 `reason === 'killed'`（Chromium 主动杀，通常是 TDR 恢复）也记日志，但不降级。

> 这一步不改任何 UI 结构，用户能直接在设置里看到「强制启用 GPU」已经变成关闭。

### 3.2 P0：无响应看门狗 + 一键恢复

对**游戏窗口宿主 **和** 每个 webview 客进程**都挂：

- `webContents.on('unresponsive')` → 写日志快照（哪个窗口/tab、当前倍率、抓包模式、进程数、各进程内存/CPU、距离上次响应的时间）；
- 弹窗询问：
  > 「游戏窗口无响应。可能是在加载战斗资源，也可能已经卡死。」
  > [继续等待] [重新加载页面] [只记录，不再提示本次]
  - **重新加载页面** = `webContents.reload()`，游戏进度不丢（服务端有会话），能救回大部分情况；
  - **继续等待** = 只关掉弹窗，之后 `responsive` 时再写一条恢复日志。
- `webContents.on('responsive')` → 写日志「已恢复，卡顿时长 X 秒」，并清掉本次的提示闸门。

> 注意：主进程本身是独立的，渲染层卡住时弹窗仍然可用，这是能自愈的关键。

### 3.3 P0：渲染进程崩溃自动恢复

`webContents.on('render-process-gone', (e, details))`：

- 写 `ERROR` 日志（reason：`crashed` / `oom` / `killed` 等）；
- 若是 `oom` 或 `crashed`，自动 `reload()` 一次（每个窗口 60 秒内最多一次，避免崩溃循环）；
- 恢复失败（再崩）则弹「请关闭其他标签页/多开窗口后重试」。

### 3.4 P1：诊断增强（让下次卡死有据可查）

现有 `perf.log` 每 60 秒只记进程数和总内存。补充：

- 每个进程单独记录：类型（browser / renderer / GPU / utility）+ 内存 + **CPU%**；
- 卡死/恢复/崩溃事件单独一行标记：`[HANG]` / `[RECOVER]` / `[CRASH]`，带当时窗口数、倍率、抓包模式；
- 日志时间戳精确到毫秒。

这样用户复现一次，把 `perf.log` 发过来就能判断是 GPU、OOM 还是 CPU。

### 3.5 P2（可选）：软件渲染「兼容模式」

设置 → 性能 新增开关 **软件渲染（兼容模式）**：

- 开启后启动参数加 `--disable-gpu` + `--disable-gpu-compositing`（走 CPU 渲染）；
- 用于「显卡驱动本身就有问题、连不强制也卡死」的机器；
- 代价：帧率下降、CPU 占用升高，只建议卡死无法解决时使用；
- 与「强制启用 GPU」互斥（软件渲染开启时忽略后者）。

## 4. 影响文件

| 文件 | 改动 |
| --- | --- |
| `main.js` | `child-process-gone` 监听 + 自动降级；窗口/webview 的 `unresponsive` / `responsive` / `render-process-gone` 监听与恢复；`perf.log` 增强；启动时的一次性提示；P2 的启动开关 + 设置开关（若做） |
| 无需改 `game.html` / `browser.html` | 全部在主进程侧完成 |
| `package.json` | 不改 |

## 5. 边界与异常

| 场景 | 处理 |
| --- | --- |
| 一进游戏就 GPU 崩溃循环 | 只降级一次（写的是 `forceGpu=false`），不会反复弹窗 |
| 卡死弹窗时用户正在战斗 | 默认按钮是「继续等待」，不误触重载 |
| 同一窗口反复崩溃 | 60 秒内只自动 reload 一次，避免无限循环 |
| 多开多窗口 | 每个窗口/webview 独立记录，日志带窗口槽位与 tab 序号 |
| 关闭性能诊断 | `[HANG]` / `[CRASH]` 这类关键事件仍然写盘（走 WARN/ERROR 通道），不受开关影响 |
| 软件渲染开启 + 强制 GPU 开启 | 软件渲染优先，忽略强制 GPU |

## 6. 预期结果

- 因显卡驱动导致的卡死：**崩一次后自动降级**，不会每次进战斗都卡死；用户能看到设置里已自动关闭。
- 因资源加载短暂卡住：弹出提示，可直接「重新加载页面」救回，不必强关整个启动器。
- 因 OOM/渲染崩溃：自动恢复一次，并在 `perf.log` 留下原因。
- 下次再有人反馈卡死，让 TA 开「性能诊断日志」复现一次，`perf.log` 里能直接看到是 GPU / 内存 / CPU 哪一类。

## 7. 待确认

1. 范围：**只做 P0（自动降级 + 看门狗 + 崩溃恢复）**，还是 **P0 + P1（诊断增强）**，还是 **全做含 P2（软件渲染开关）**？
   - 建议：P0 + P1 一起做（卡死原因不发日志的话，后续很难定位）；P2 建议也做，它是驱动级卡死唯一的兜底。
2. 「无响应」弹窗是否接受？（默认 3 个按钮：继续等待 / 重新加载页面 / 本次不再提示）
3. GPU 崩溃后自动把「强制启用 GPU」关掉这个行为是否接受？（默认接受，并在启动器里提示一次）
