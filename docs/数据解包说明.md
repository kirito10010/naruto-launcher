# 火影忍者Online · 数据解包说明

> 这份文档只回答一个问题：**拿到一段数据，怎么把它解成可读字段。**
> 覆盖：netlog 里的 TCP 游戏协议、http jsonl 里的 HTTP/WebSocket、以及 .cfg / .pkg / .xml / .swf 这些资源文件。

---

## 0. 一页速查：什么数据用什么解

先看这张表，90% 的情况照着做就行。

| 拿到的数据 | 判定信号 | 用什么解 |
| --- | --- | --- |
| netlog `params.bytes` | base64 字符串 | `Buffer.from(s, 'base64')` → 得到 socket 原始字节 |
| socket 字节流 | 出现 `09 01` + 2 字节长度 + 4 字节 cmd | 按 36 字节头**分帧**（见 §3） |
| 帧 `type=1` / `type=2` | 头里第 12 字节起的 u32 | **必定 TEA 加密**（§5） |
| 帧 `type=3` | 同上 | **先按明文试**；解析失败且 `len%8==0 && len>=16` → 按 TEA 解 |
| 解密/明文结果首字节 `0x0A` / `0x08` / `0x12` | 能完整走完 Protobuf | 直接 **裸解 Protobuf**（§6） |
| 首字节 `0x78` | 第二字节 `9C`/`DA`/`01` | `zlib.inflateSync()` |
| 首字节 `0x43 0x57 0x53`（`CWS`） | SWF | 去掉 8 字节头后 `zlib.inflateSync()`，前面补 `FWS` |
| 首字节 `0x5A 0x57 0x53`（`ZWS`） | SWF | **LZMA** 解压（Node 原生不支持，需 LZMA 实现） |
| 首字节 `0x46 0x57 0x53`（`FWS`） | SWF | 本来就是明文，直接读 |
| 首字节 `0x50 0x4B`（`PK`） | zip | 按 zip 解（或 `zlib` 逐条） |
| HTTP body `base64: true` | JSONL 里 `"base64":true` | `Buffer.from(body,'base64')` |
| HTTP body `base64: false` | 文本类 mime | `Buffer.from(body,'latin1')`；**二进制会失真，能重抓就用 netlog** |
| 后缀 `.cfg` | 网络资源 | zlib 解压 → 自定义 TLV（§7.1） |
| 后缀 `.pkg` | 网络资源 | zlib 解压 → 文件表切分（§7.2） |
| `resource.cfg` | 主资源索引 | **LZMA**，不是 zlib |
| 后缀 `.xml` | 配置 | 先试 UTF-8，再试 GBK（`new TextDecoder('gbk')`） |
| 首字节 `78 FD` 且 inflate 失败 | 少数 XML 资源 | Flash 自定义压缩，**目前无解，跳过**（不影响业务数据） |

## 1. 数据从哪来

```
Electron / Chromium
   ├─ net-log ──▶ netlog-<ts>.json   网络栈事件 + socket 原始字节（游戏协议唯一来源）
   └─ CDP ──────▶ http-<ts>.jsonl    HTTP 请求/响应 + 响应体 + WebSocket 帧

离线解包（Node，零依赖）
   分流 ──▶ 分帧 ──▶ 判明文/密文 ──▶ TEA ──▶ Protobuf ──▶ 可读字段
```

抓包阶段只有三个硬性前提，其余都在退出后离线做：

1. 启动参数必须带 `--log-net-log=<文件>` **和** `--net-log-capture-mode=IncludeSocketBytes`；
2. 必须正常退出（托盘「退出」），强杀会截断 netlog 尾部；
3. netlog 动辄几十上百 MB，解析时给 Node 加内存：`node --max-old-space-size=8192`。

## 2. 解 netlog：先分清「事件」和「字节」

### 2.1 文件结构

```json
{
  "constants": { "logEventTypes": { "1": "TCP_CONNECT", "87": "SOCKET_BYTES_RECEIVED" } },
  "events": [
    { "source": { "id": 602 }, "type": 87, "time": "19059619", "params": { "bytes": "CQ..." } }
  ]
}
```

- `logEventTypes` 是 `数字 → 名字`，先反转成 `名字 → 数字` 才能按名字筛。
- `source.id` 是 socket / 请求的归属，**同一个 id 才属于同一条连接**。
- `params.bytes` 是 base64 的原始字节。
- `time` 是毫秒级 tick，**同一个文件内的不同事件可以直接相减**（§9 会用到）。

### 2.2 找游戏连接

游戏走 `zone.huoying.qq.com:11096`（IP 会变）。做法：

1. 扫 `TCP_CONNECT` / `TCP_CONNECT_ATTEMPT`，`params.address` 里包含 `:11096` 的记下 `source.id`；
2. 同一端口可能有多个 socket（策略文件连接 + 主连接），**按收到字节总量取最大的那个**。

> 实测两份抓包的主连接 id 分别是 `602` 和 `1262`——**不要写死 id**。

### 2.3 分流：rx 和 tx 必须分开

```js
if (t === 'SOCKET_BYTES_RECEIVED') rx.push(buf);   // 服务端 → 客户端
if (t === 'SOCKET_BYTES_SENT')     tx.push(buf);   // 客户端 → 服务端
```

**这是最容易踩的坑**：把两个方向拼成一条流，帧会全部错位，`cmd` 变成乱码。按事件顺序各自 `Buffer.concat` 即可，实测不需要按 TCP 序号重排。

## 3. 解帧：固定 36 字节头

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 2 | magic | 固定 `09 01` |
| 2 | 2 | length | 载荷长度（大端） |
| 4 | 4 | cmdId | 命令号（大端） |
| 8 | 4 | index | 请求/响应序号 |
| 12 | 4 | type | `1`=客户端上行，`2`=服务端下行，`3`=服务端推送 |
| 16 | 8 | reserved | |
| 24 | 4 | selfUin | |
| 28 | 2 | selfRole | |
| 30 | 2 | serId | |
| 32 | 4 | reserved | |

载荷 = 第 36 字节起、长度 `length`。

```js
const HDR = 36;
function frames(d) {
  const out = []; let off = 0;
  while (off + HDR <= d.length) {
    if (d[off] !== 0x09 || d[off + 1] !== 0x01) { off++; continue; }  // 错位，继续找
    const len = d.readUInt16BE(off + 2);
    if (off + HDR + len > d.length) break;                           // 这帧还没收全
    out.push({
      cmd: d.readUInt32BE(off + 4),
      idx: d.readUInt32BE(off + 8),
      type: d.readUInt32BE(off + 12),
      p: d.slice(off + HDR, off + HDR + len)
    });
    off += HDR + len;
  }
  return out;
}
```

> magic 只有 2 字节，可能在载荷里偶然撞上。判据是**长度连续性**：从帧头开始 `off += 36 + len` 必须始终落在下一个 `09 01` 上。

## 4. 核心：一眼判断该不该解密

**`type` 不能作为唯一依据。**

| type | 实测 |
| --- | --- |
| 1 | 上行，加密（`len%8!=0` 的少数是明文，如登录 skey、选服） |
| 2 | 下行，加密 |
| 3 | **混合**：有明文 Protobuf，也有加密帧 |

实测 `type=3` 且加密的推送有：`261969`、`253957`、`197389`、`197387`、`199168`、`198149`、`198146`、`198153`、`1048579` 等。如果按「type=3 就是明文」处理，这些帧会全是乱码。

### 判定顺序

```js
function looksPlain(buf) {
  // 能完整走完 Protobuf（允许尾部补 0）→ 认为明文
  return buf.length > 0 && pbFull(buf);
}

function decodePayload(f) {
  if (f.type === 3) {
    if (looksPlain(f.p)) return { data: f.p, mode: 'plain' };
    if (f.p.length % 8 === 0 && f.p.length >= 16) return { data: strip(teaDec(f.p), f.p.length), mode: 'tea' };
    return null;
  }
  if (f.p.length % 8 === 0 && f.p.length >= 16) return { data: strip(teaDec(f.p), f.p.length), mode: 'tea' };
  return { data: f.p, mode: 'plain' };   // 极少数未加密的小帧
}
```

### 自检

- 解出来首字节通常是 `0x0A`（field 1，长度前缀）或 `0x08`（field 1，varint）；
- 能完整解析出字段 → 对了；
- 全随机字节 → 参数不对，或者这条其实没加密。

## 5. TEA 解密（腾讯 QQ 变体）

### 5.1 参数

| 项 | 值 |
| --- | --- |
| key | `d796c2542916b456`（**16 字节 ASCII**，不是 hex） |
| 轮数 | 16 |
| DELTA | `0x9E3779B9` |
| 首组初值 | `s = DELTA << 4` |
| 链模式 | 每组用**前一组明文**异或当前密文，解完再异或前一组密文 |
| 头部 | `1 字节(低 3 位=pad) + pad 字节 + 2 字节 salt` |
| 尾部 | 7 字节 0 |

### 5.2 算法

```js
const DELTA = 0x9E3779B9;
const KEY = Buffer.from('d796c2542916b456', 'latin1');
const u32 = (x) => x >>> 0;
const K = [KEY.readUInt32BE(0), KEY.readUInt32BE(4), KEY.readUInt32BE(8), KEY.readUInt32BE(12)];

function teaDec8(b, o) {
  let v0 = b.readUInt32BE(o), v1 = b.readUInt32BE(o + 4), s = u32(DELTA << 4);
  for (let i = 0; i < 16; i++) {
    v1 = u32(v1 - u32(u32(u32(v0 << 4) + K[2]) ^ u32(v0 + s) ^ u32(u32(v0 >>> 5) + K[3])));
    v0 = u32(v0 - u32(u32(u32(v1 << 4) + K[0]) ^ u32(v1 + s) ^ u32(u32(v1 >>> 5) + K[1])));
    s = u32(s - DELTA);
  }
  const out = Buffer.alloc(8);
  out.writeUInt32BE(v0, 0); out.writeUInt32BE(v1, 4);
  return out;
}

function teaDec(d) {
  const n = d.length / 8;
  if (!Number.isInteger(n) || n < 2) return null;
  let p = teaDec8(d, 0);
  const out = [p];
  for (let i = 1; i < n; i++) {
    const x = Buffer.alloc(8);
    for (let j = 0; j < 8; j++) x[j] = p[j] ^ d[i * 8 + j];
    p = teaDec8(x, 0);
    const o = Buffer.alloc(8);
    for (let j = 0; j < 8; j++) o[j] = p[j] ^ d[(i - 1) * 8 + j];
    out.push(o);
  }
  return Buffer.concat(out);
}

function strip(full, total) {
  if (!full) return null;
  // 注意：pad 取的是**解密后**首字节的低 3 位
  const pad = full[0] & 7;
  const n = total - 1 - pad - 2 - 7;
  return n < 0 ? null : full.slice(1 + pad + 2, 1 + pad + 2 + n);
}

const decode = (payload) =>
  payload.length % 8 === 0 && payload.length >= 16 ? strip(teaDec(payload), payload.length) : null;
```

> 注意 `strip` 的偏移用 `full[0] & 7`，不是密文的 `payload[0]`。用错会解出 1~7 字节的偏移垃圾。

## 6. 解 Protobuf（无 schema 裸解）

### 6.1 规则

- `varint`：每字节低 7 位是数据，最高位 1 表示继续。
- `key = varint`；`field = key >>> 3`，`wireType = key & 7`。
- wireType：`0`=varint，`1`=64 位，`2`=长度前缀，`5`=32 位。

```js
function readVarint(b, i) {
  let r = 0, s = 0;
  while (i < b.length) {
    const x = b[i++];
    r += (x & 0x7f) * 2 ** s;
    if (!(x & 0x80)) return [r, i];
    s += 7;
    if (s > 63) return null;
  }
  return null;
}

function pb(b) {
  const out = []; let i = 0;
  while (i < b.length) {
    const kv = readVarint(b, i); if (!kv) break;
    const [k, i2] = kv; i = i2;
    const f = k >>> 3, wt = k & 7;
    if (!f) break;
    if (wt === 0) { const v = readVarint(b, i); if (!v) break; out.push([f, v[0]]); i = v[1]; }
    else if (wt === 2) {
      const v = readVarint(b, i); if (!v) break;
      i = v[1]; if (i + v[0] > b.length) break;
      out.push([f, b.slice(i, i + v[0])]); i += v[0];
    }
    else if (wt === 5) { if (i + 4 > b.length) break; out.push([f, b.readUInt32LE(i)]); i += 4; }
    else if (wt === 1) { if (i + 8 > b.length) break; out.push([f, 0]); i += 8; }
    else break;   // wt 3/4/6/7 非法 → 停
  }
  return out;
}
```

### 6.2 「长度前缀」是字符串还是子消息

同一个 wireType 2 两种都可能，只能试：

```js
function isUtf8Like(buf) {
  if (!buf || !buf.length) return false;
  const s = buf.toString('utf8');
  if (s.includes('\uFFFD')) return false;
  let ok = 0, n = 0;
  for (const ch of s) { n++; const c = ch.codePointAt(0); if (c >= 0x20) ok++; }
  return ok / n > 0.9;
}
```

能当 UTF-8 → 当字符串；否则递归当子消息。中文字段一定走字符串分支。

### 6.3 打印成树

```js
function dump(b, indent = '', depth = 3) {
  let s = '';
  for (const [f, v] of pb(b)) {
    if (!Buffer.isBuffer(v)) { s += `${indent}${f}: ${v}\n`; continue; }
    if (isUtf8Like(v)) s += `${indent}${f}: "${v.toString('utf8').replace(/[\x00-\x1f]/g, '.')}"\n`;
    else {
      s += `${indent}${f}: <${v.length}B ${v.slice(0, 12).toString('hex')}>\n`;
      if (depth > 0 && v.length) s += dump(v, indent + '  ', depth - 1);
    }
  }
  return s;
}
```

### 6.4 业务字段惯例（实测）

| 模式 | 含义 |
| --- | --- |
| `{1:{1:0, 2:"success"}}` | 通用成功回包（几乎所有业务命令外层都套这个） |
| 顶层重复 `2:<子消息>` | 列表：每条是一个对象 |
| 10 位整数（`1793944320`） | Unix 秒级时间戳 |
| 成对时间戳 | 活动/商品有效期 `[开始, 结束]`；差值 86400=24h、54000=15h |
| `{1: itemId, 2: count}` | 物品与数量 |
| `{1: 商店ID, 2:{1: 0/1/2}}` | 商店请求：0=商品列表，2=购物车/其它页 |
| 数字 `0/1/2/3` 尾部 | 状态位，不确定就留原值 |

**itemId 段位（观测，非官方）**：`1019xxxx` 消耗品/礼包/充值档位，`1060xxxx` 技能突破书，`2040xxxx` 忍者碎片/装备，`11000001` 点券类货币。

## 7. 解资源文件

### 7.1 `.cfg`（配置表，最重要的资源类型）

1. 拿到字节，首字节 `0x78` → `zlib.inflateSync()`；
2. 解压后是「表头 + 行数据」，值编码是自定义 TLV：

| 标记 | 含义 |
| --- | --- |
| `0x04` + varint | 整数 |
| `0x06` + varint(`len<<1\|1`) + UTF-8 | 字符串 |
| `0x05` + 8 字节 | double |
| 裸 `varint(len<<1\|1)` + UTF-8 | 字段名 / 表名 |

实测：解压后直接当 **UTF-8** 文本扫字符串，就能拿到 `名称 + 描述 + 数字 ID` 三元组。例：`item3.pkg` 里可以搜到「招募，升星蝎[绯流琥]所需材料」和对应 `20400447`。

```js
const zlib = require('zlib');
const raw = fs.readFileSync('CommonItemCFG.cfg');
const data = raw[0] === 0x78 ? zlib.inflateSync(raw) : raw;
const text = new TextDecoder('utf-8').decode(data);   // Node 14+ 自带 ICU，也支持 'gbk'
```

### 7.2 `.pkg`（压缩归档）

zlib 解压后是多个文件拼接：`文件名 + u32 长度 + 内容` 循环切分。实测 `config/archives/item1~3.pkg` 解压后是忍者/道具的全量索引（几 MB 文本 + 二进制字段）。

### 7.3 `.xml`

- 多数是 UTF-8，少数是 GBK：`new TextDecoder('gbk').decode(buf)`；
- 首字节 `78 9C/DA` → 先 inflate；
- 首字节 `78 FD` 且 inflate 报错 → Flash 自定义压缩，**目前无解**，直接跳过。

### 7.4 `.swf`

| 头 | 处理 |
| --- | --- |
| `FWS` | 原样 |
| `CWS` | `Buffer.concat([Buffer.from('FWS'), buf.slice(3,8), zlib.inflateSync(buf.slice(8))])` |
| `ZWS` | LZMA（Node 原生没有，需引入实现；`resource.cfg` 同理） |

> 大部分业务数据**不在 SWF 里**，SWF 只是 UI。真正的商品/活动数据走 TCP 或 `.cfg`，别在 SWF 上耗太久。

### 7.5 图片/音频/字体

`.jpg/.png/.mp3/.bmp` 都是原文件，直接从 HTTP body 的 base64 还原即可，不需要额外解码。

## 8. 解 HTTP / WebSocket（jsonl）

每行一个 JSON，按 `id` 关联：

| `type` | 含义 | 关键字段 |
| --- | --- | --- |
| `req` | 请求 | `url / method / postData / ts` |
| `res` | 响应头 | `status / mime / headers` |
| `body` | 响应体 | `body / base64 / len` |
| `ws-open` / `ws-sent` / `ws-received` | WebSocket | `payload / opcode` |

```js
const map = new Map();
for (const line of lines) {
  const o = JSON.parse(line);
  if (!o.id) continue;
  const e = map.get(o.id) || {};
  map.set(o.id, e);
  if (o.type === 'req') { e.url = o.url; e.method = o.method; }
  if (o.type === 'res') { e.status = o.status; e.mime = o.mime; }
  if (o.type === 'body') { e.body = o.body; e.base64 = o.base64; }
}
const raw = e.base64 ? Buffer.from(e.body, 'base64') : Buffer.from(e.body, 'latin1');
```

> 坑：`base64:false` 的二进制（压缩过的 `.cfg`）已经被当字符串解码过一次，字节失真。**要二进制就回 netlog 取。**

## 9. 怎么定位「刚点的那个面板」的数据

这是实战里最有用的一招，比盲猜 cmd 快得多。

1. 在 netlog 里搜目标资源的 URL 事件（例如 `ShopDiscountUI.swf`），取它的 `time` 作为锚点 `T`；
2. 给每条 RX 帧记录它所在 chunk 的 `time`；
3. 按 `dt = 帧time - T` 排序，**`dt` 在 0~2000ms 内的就是该面板的请求/响应**。

实战例子（打开商城特惠）：

```
T = 19059619（ShopDiscountUI.swf 开始加载）
+180ms  cmd=1051712  充值档位
+250ms  cmd=1048608  商城商品列表（16 条）
+328ms  cmd=1048608  购物车（空）
```

如果没有落在窗口内的帧，说明这个面板的数据**没有走 TCP**（可能是本地缓存 / HTTP / 尚未请求），别再硬解了。

> 同理：用户点了「加入购物车」但抓包里没出现新请求，通常是面板数据还没刷新，或者操作发生在抓包结束之后。

### 10.1 商城特惠：`1048608` 字段表（2026-11-06 抓包，与游戏内截屏 16/16 核对）

**请求**

```
f1 = 商店ID = 活动ID × 2        商城特惠 = 1600552（活动 800276）
f2 = { f1: 0 }                 0 = 商品列表
f2 = { f1: 2 }                 2 = 购物车（没买东西时响应里 f3 长度为 0）
```

**响应**

```
f1 = { f1: 0, f2: "success" }  状态
f2 = { f1: 活动开始, f2: 活动结束 }
f3 = 容器（内部是重复的 f2 商品对象）  ← 注意：f3 是一整块，不是重复 f3
```

**商品对象**

| 字段 | 含义 | 缩放 |
| --- | --- | --- |
| f1 | 槽位（界面排序） | — |
| f2.f1 | 物品 ID | — |
| f2.f2 | 物品类型 | — |
| f3 | **每日限购** | **÷2** |
| f4 | 已购数量 | — |
| f7 | **折扣价** | **÷2** |
| f9 | 货币类型（1 = 点券） | — |
| f11 | 当日窗口开始 | — |
| f12 | 当日窗口结束 | — |

**两个坑**

1. **f3 / f7 存的是「实际值 × 2」**。之前误以为「每日限购不在响应里」，其实是被 ×2 挡住了（160 → 80、360 → 180、800 → 400）。
2. **f3 是容器**：`pb(响应).f3` 得到一整块 buffer，再 `pb` 一次才拿到重复的 `f2` 商品对象。直接把 f3 当商品对象解，会把「槽位」误当成「物品 ID」（本次实测首个物品会解出 `34`）。

**时间**

- 全部是 UTC 秒，展示要 +8 小时。
- `f2` 是总活动时间：`1793826000 ~ 1794412799` = `2026-11-05 05:00:00（周四） ~ 2026-11-11 23:59:59（周三）`。
- 商品的 `f11/f12` 是**当日窗口**：`1793912400 ~ 1793998799` = `2026-11-06 05:00:00（周五） ~ 2026-11-07 04:59:59（周六）`，即「每天 05:00 刷新，窗口 24 小时」。
- 界面上的「限时12小时」不是独立字段，就是「抓包时刻 → f12」的剩余时间（17:0x 抓包 → 约 12 小时）。
- 界面「80/80个」= `剩余/上限`，`剩余 = 每日限购 - f4`。

**商品图标**

- 路径形如 `https://res.huoying.qq.com/<版本目录>/assets/bag/item/<物品ID>.png`。
- `<版本目录>`（如 `NarutoBeta9.05Build301`）是**逐个资源**版本化的，同一批商品会落在不同目录，**不能按 ID 拼**（实测 3 个 ID × 5 个目录，除真实路径外全 404）。
- 只能从会话的 `http-*.jsonl` 里取游戏真实请求过的 URL；没滚到的卡片不会有请求，也就没有图。

## 11. 排错对照表

| 现象 | 原因 / 处理 |
| --- | --- |
| netlog 没有 `SOCKET_BYTES_*` | 少了 `IncludeSocketBytes` |
| `JSON.parse` 失败 / 尾部截断 | 抓包时被强杀，没正常退出 |
| 帧 cmd 全是乱码、长度离谱 | rx/tx 拼在一起了；或扫到载荷里的假 magic |
| 小帧正常、大帧全乱 | 只解了 `type!=3`，漏了加密的 `type=3` |
| 解密结果整体偏移几个字节 | `strip` 的 pad 用了密文首字节，应改用解密后首字节 |
| 解出来全是随机字节 | 该帧没加密却硬解；或 key/参数不对 |
| `pb()` 越界 | 明文长度不对（解密失败 / 拿错帧） |
| 中文乱码 | 解的是 GBK 资源，用 `TextDecoder('gbk')` |
| CDP body 是乱码 | 二进制被当字符串解码，改用 netlog |
| 面板数据完全找不到 | 用 §9 时间对齐确认请求是否真的发生；可能需翻页/换页签 |

## 12. 完整可运行脚本

保存为 `unpack.js`，用法：

```bash
node --max-old-space-size=8192 unpack.js netlog-xxx.json 11096
DUMP=1048608,199458 node unpack.js netlog-xxx.json 11096   # 额外打印指定命令的字段树
```

```js
const fs = require('fs');

const FILE = process.argv[2];
const PORT = process.argv[3] || '11096';
const DUMP = new Set((process.env.DUMP || '').split(',').filter(Boolean).map(Number));
if (!FILE) { console.log('用法: node unpack.js <netlog.json> [port]'); process.exit(1); }

const HDR = 36, SALT = 2, ZERO = 7, DELTA = 0x9E3779B9;
const KEY = Buffer.from('d796c2542916b456', 'latin1');
const u32 = (x) => x >>> 0;
const K = [KEY.readUInt32BE(0), KEY.readUInt32BE(4), KEY.readUInt32BE(8), KEY.readUInt32BE(12)];

/* ---------- TEA ---------- */
function teaDec8(b, o) {
  let v0 = b.readUInt32BE(o), v1 = b.readUInt32BE(o + 4), s = u32(DELTA << 4);
  for (let i = 0; i < 16; i++) {
    v1 = u32(v1 - u32(u32(u32(v0 << 4) + K[2]) ^ u32(v0 + s) ^ u32(u32(v0 >>> 5) + K[3])));
    v0 = u32(v0 - u32(u32(u32(v1 << 4) + K[0]) ^ u32(v1 + s) ^ u32(u32(v1 >>> 5) + K[1])));
    s = u32(s - DELTA);
  }
  const out = Buffer.alloc(8);
  out.writeUInt32BE(v0, 0); out.writeUInt32BE(v1, 4);
  return out;
}
function teaDec(d) {
  const n = d.length / 8;
  if (!Number.isInteger(n) || n < 2) return null;
  let p = teaDec8(d, 0);
  const out = [p];
  for (let i = 1; i < n; i++) {
    const x = Buffer.alloc(8);
    for (let j = 0; j < 8; j++) x[j] = p[j] ^ d[i * 8 + j];
    p = teaDec8(x, 0);
    const o = Buffer.alloc(8);
    for (let j = 0; j < 8; j++) o[j] = p[j] ^ d[(i - 1) * 8 + j];
    out.push(o);
  }
  return Buffer.concat(out);
}
function strip(full, total) {
  if (!full || !full.length) return null;
  const pad = full[0] & 7;
  const n = total - 1 - pad - SALT - ZERO;
  return n < 0 ? null : full.slice(1 + pad + SALT, 1 + pad + SALT + n);
}

/* ---------- 帧 ---------- */
function frames(d) {
  const out = []; let off = 0;
  while (off + HDR <= d.length) {
    if (d[off] !== 0x09 || d[off + 1] !== 0x01) { off++; continue; }
    const len = d.readUInt16BE(off + 2);
    if (off + HDR + len > d.length) break;
    out.push({
      cmd: d.readUInt32BE(off + 4),
      idx: d.readUInt32BE(off + 8),
      type: d.readUInt32BE(off + 12),
      p: d.slice(off + HDR, off + HDR + len)
    });
    off += HDR + len;
  }
  return out;
}

/* ---------- Protobuf ---------- */
function rv(b, i) {
  let r = 0, s = 0;
  while (i < b.length) {
    const x = b[i++];
    r += (x & 0x7f) * 2 ** s;
    if (!(x & 0x80)) return [r, i];
    s += 7;
    if (s > 63) return null;
  }
  return null;
}
function pb(b) {
  const out = []; let i = 0;
  while (i < b.length) {
    const kv = rv(b, i); if (!kv) break;
    const [k, i2] = kv; i = i2;
    const f = k >>> 3, wt = k & 7;
    if (!f) break;
    if (wt === 0) { const v = rv(b, i); if (!v) break; out.push([f, v[0]]); i = v[1]; }
    else if (wt === 2) {
      const v = rv(b, i); if (!v) break;
      i = v[1]; if (i + v[0] > b.length) break;
      out.push([f, b.slice(i, i + v[0])]); i += v[0];
    }
    else if (wt === 5) { if (i + 4 > b.length) break; out.push([f, b.readUInt32LE(i)]); i += 4; }
    else if (wt === 1) { if (i + 8 > b.length) break; out.push([f, 0]); i += 8; }
    else break;
  }
  return out;
}
function pbFull(b) {
  // 能完整走完（允许尾部补 0）才算明文
  let i = 0, fields = 0;
  while (i < b.length) {
    const kv = rv(b, i); if (!kv) break;
    const [k, i2] = kv; i = i2;
    const f = k >>> 3, wt = k & 7;
    if (!f || wt > 5 || wt === 3 || wt === 4) break;
    if (wt === 0) { const v = rv(b, i); if (!v) break; i = v[1]; }
    else if (wt === 2) {
      const v = rv(b, i); if (!v) break;
      i = v[1]; if (v[0] < 0 || i + v[0] > b.length) break;
      i += v[0];
    }
    else if (wt === 5) i += 4;
    else if (wt === 1) i += 8;
    if (i > b.length) break;
    fields++;
  }
  if (!fields) return false;
  for (let j = i; j < b.length; j++) if (b[j] !== 0) return false;
  return true;
}
function isUtf8Like(buf) {
  if (!buf || !buf.length) return false;
  const s = buf.toString('utf8');
  if (s.includes('\uFFFD')) return false;
  let ok = 0, n = 0;
  for (const ch of s) { n++; const c = ch.codePointAt(0); if (c >= 0x20) ok++; }
  return ok / n > 0.9;
}
function dump(b, indent = '', depth = 3) {
  let s = '';
  for (const [f, v] of pb(b)) {
    if (!Buffer.isBuffer(v)) { s += `${indent}${f}: ${v}\n`; continue; }
    if (isUtf8Like(v)) s += `${indent}${f}: "${v.toString('utf8').replace(/[\x00-\x1f]/g, '.')}"\n`;
    else {
      s += `${indent}${f}: <${v.length}B ${v.slice(0, 12).toString('hex')}>\n`;
      if (depth > 0 && v.length) s += dump(v, indent + '  ', depth - 1);
    }
  }
  return s;
}

/* ---------- 主流程 ---------- */
const log = JSON.parse(fs.readFileSync(FILE, 'utf8'));
const typeName = {};
for (const [k, v] of Object.entries(log.constants.logEventTypes)) typeName[v] = k;

// 1) 找游戏 socket（按收字节最多）
const ids = new Set();
for (const ev of log.events) {
  const t = typeName[ev.type];
  if (t !== 'TCP_CONNECT' && t !== 'TCP_CONNECT_ATTEMPT') continue;
  const p = ev.params || {};
  const addr = [p.address, p.host, p.hostname, p.remote_address, p.destination].filter(Boolean).join(' ');
  if (addr.includes(':' + PORT) && ev.source && ev.source.id != null) ids.add(ev.source.id);
}
let best = null;
for (const id of ids) {
  const rx = [];
  for (const ev of log.events) {
    if (!ev.source || ev.source.id !== id) continue;
    if (typeName[ev.type] !== 'SOCKET_BYTES_RECEIVED') continue;
    if (typeof ev.params.bytes !== 'string') continue;
    rx.push(Buffer.from(ev.params.bytes, 'base64'));
  }
  const b = Buffer.concat(rx);
  if (!best || b.length > best.buf.length) best = { id, buf: b };
}
if (!best) { console.log('没有找到端口 ' + PORT + ' 的连接'); process.exit(1); }
console.log('socket=' + best.id + ' rx=' + best.buf.length);

// 2) 分流 tx（单独拼，别和 rx 混）
const txChunks = [];
for (const ev of log.events) {
  if (!ev.source || ev.source.id !== best.id) continue;
  if (typeName[ev.type] !== 'SOCKET_BYTES_SENT') continue;
  if (typeof ev.params.bytes !== 'string') continue;
  txChunks.push(Buffer.from(ev.params.bytes, 'base64'));
}

// 3) 分帧 + 解密
function decodeFrame(f) {
  if (f.type === 3 && pbFull(f.p)) return { data: f.p, mode: 'plain' };
  if (f.p.length % 8 === 0 && f.p.length >= 16) {
    const d = strip(teaDec(f.p), f.p.length);
    return d ? { data: d, mode: 'tea' } : null;
  }
  return { data: f.p, mode: 'plain' };
}

const stat = new Map();
for (const f of frames(best.buf)) {
  stat.set(f.cmd, (stat.get(f.cmd) || 0) + 1);
  const r = decodeFrame(f);
  const head = `cmd=${f.cmd} idx=${f.idx} type=${f.type} len=${f.p.length} ${r ? r.mode : 'raw'}`;
  if (!r) { console.log(head + ' (解不开)'); continue; }
  const txt = r.data.toString('utf8').replace(/[^\x20-\x7e\u4e00-\u9fff]/g, '.');
  console.log(head + ' | ' + txt.slice(0, 160));
  if (DUMP.has(f.cmd)) console.log(dump(r.data, '  '));
}
// 4) 上行帧也打一份（请求往往带参数）
console.log('\n--- TX ---');
for (const f of frames(Buffer.concat(txChunks))) {
  const r = decodeFrame(f);
  console.log(`cmd=${f.cmd} idx=${f.idx} type=${f.type} len=${f.p.length} ${r ? r.mode : 'raw'} | ` +
    (r ? r.data.toString('hex') : f.p.toString('hex')));
}

console.log('\n命令号统计：');
for (const [cmd, n] of [...stat.entries()].sort((a, b) => b[1] - a[1])) console.log('  ' + cmd + ' × ' + n);
```

## 13. 一句话总结

**能读的优先当明文，读不通再看长度是否 8 的倍数去解 TEA，解完按 Protobuf 裸解；资源按后缀选 inflate / LZMA / 文本编码。**
数据找不到时，先用时间对齐确认「请求到底发生了没有」，再决定要不要继续挖。

## 14. 先在启动器里试 URL：网址调试

不确定某份数据是走 HTTP 还是走 TCP 时，先用「网址调试」窗口试一遍，成本最低。

**入口**：游戏窗口「⋯ 更多」→「网址调试」；托盘右键 →「网址调试」。

**它能做什么**
- 自动填入当前标签页的 URL，可以直接改路径、改 query、改版本号（`NarutoBetaX.XXBuildNNN`）后重新发送；
- **复用当前游戏标签的会话分区**（`persist:qq-<QQ>`），带 Cookie/登录态，不再是外部浏览器的游客身份；
- 直接显示状态码、响应头、耗时、大小，正文按 JSON/XML/文本/二进制自动切换显示；
- 二进制响应可以「保存到桌面」，后续直接套用本文档的解包流程；
- 最近 50 条请求有历史，点一下就能回填。

**它不能做什么（别浪费时间）**
- 看不到游戏 TCP（`zone.huoying.qq.com:11096`）里的任何东西——商城商品、背包、活动数据都在那里；
- 不做请求拦截、不改游戏流量，也不做 TCP 重放。

**判断规则**
- 在网址调试里能拿到的数据 → 用本文档第 7、8 节的方法解（`.cfg/.pkg/.xml/.swf`、HTTP body）；
- 怎么改参数都拿不到 → 说明这份数据走的是 TCP，回到第 2~6 节，用抓包 + 分帧 + TEA + Protobuf 去解。

## 15. 现成的解析：商城特惠抓包模式

不用自己写脚本，启动器里已经有做好的实现（`shop-export.js`），它把第 2~6 节的流程串成了一条线。

**怎么用**

1. 设置 → 抓包模式 → 选「商城特惠（导出 JSON + 图片）」→ 重启启动器；
2. 进游戏，打开「商城特惠」面板，**把商品卡片上下滚动一遍**（滚到哪张才会请求哪张图）；
3. 关闭游戏窗口 → 托盘右键 → 退出；
4. 桌面 `火影商城特惠/商城特惠_<时间>/` 里生成：
   - `商城特惠.json`：活动时间、当日窗口、每件商品的名称 / 说明 / 限购 / 已购 / 剩余 / 折扣价 / 时间范围 / 星期
   - `商城特惠.txt`：同内容的可读表格 + 「物品说明」段
   - `images/<物品ID>.png`：商品图标（按 `<src>` 取，礼包会共用同一张）
   - `导出诊断.txt`：只在缺数据/缺图时生成

**它背后的取数逻辑**

| 内容 | 来源 |
| --- | --- |
| 商品、限购、折扣价、时间 | net-log → `extractGameStream(netlog, [1048608, 199458])` → `1048608`（见 10.1） |
| 活动名与服务器时间 | `199458` 里 `f1 = 800276` 那条 |
| 物品名称 / 说明 / 图标 ID | `config/bag/conf/CommonItemCFG.xml`（明文 XML） |
| 忍者碎片的名称 / 说明 | `config/archives/item1..3.pkg`（zlib） |
| 商品图标 | 同会话 `http-*.jsonl` 里的 `assets/bag/item/<id>.png`，有响应体直接用，没有就按真实 URL 补下载 |

### 15.1 物品说明与图标 ID 从哪来

**`config/bag/conf/CommonItemCFG.xml`（明文 XML，约 2.4 MB / 3300+ 条）**

同一个表有 `.cfg`（私有二进制）和 `.xml`（明文）两份，**优先用 XML**，直接按 `<row>` 切分即可：

```xml
<row>
  <id>10190830</id>
  <name>高级试验礼袋</name>
  <src>10100038</src>          <!-- 图标资源 ID，不是物品 ID -->
  <desc>开启后获得16个高级试验剂和6个高级试验保护剂，并有一定的概率获得千手柱间[秽土转生]碎片。</desc>
  <extraDesc/>
  <showRandomItems>1</showRandomItems>
  ...
</row>
```

**关键：`<src>` 才是图标 ID。** 游戏请求的是 `assets/bag/item/<src>.png`，不是 `<id>.png`。
7 个礼包的 `<src>` 全是 `10100000`（通用礼包图），高级试验礼袋是 `10100038`——这就是以前「礼包图全都抓不到、抓到的 10100000.png 被当成无关图丢掉」的原因。

**`config/archives/item1..3.pkg`（zlib）**

忍者碎片不在物品表里，在「图鉴」包里。解压后仍是私有二进制，但可以按固定规律提字符串：

- 记录边界：`0x11` + 8 位数字 ID，到下一条同形态为止；
- 记录内字符串：`0x06` + 长度 + 内容，**长度 = 字节数 × 2 + 1**（16 字节 → `0x21`）；
- 碎片说明固定形如 `招募，升星蝎[绯流琥]所需材料。`，用 `/招募，升星(.+?)所需材料/` 取名字与说明。

实测：`20400446 → 「[绯流琥]」+「招募，升星蝎[绯流琥]所需材料。」`。

### 15.2 礼包掉落（固定 / 随机）

```
CommonItemCFG.xml   <id>10190248</id> … <val2>49900725</val2>        ← val2 就是掉落组 ID
        ▼
RewardItemTransferCFG.xml
    <row><rewardId>49900725</rewardId><itemId>10800057</itemId><num>88</num><sure>1</sure><name>洞穴密钥</name></row>
    <row><rewardId>49900725</rewardId><itemId>10810001</itemId><num>1</num><sure>0</sure><name>5级先攻符石</name></row>
```

- `sure = 1` → 固定掉落；`sure = 0` → 随机掉落；
- `<name>不获得物品</name><num>0</num>` 是占位项，要过滤；
- 实测：试验礼包 → 试验剂×50 + 试验保护剂×50；高级试验礼袋 → 高级试验剂×16 + 高级试验保护剂×6（固定）+ 千手柱间[秽土转生]×1（随机）；幸运钥匙包 → 洞穴密钥×88（固定）+ 5 种 5 级符石各 1（随机）。

### 15.3 碎片对应的忍者技能

```

        │ 正则取忍者名
        ▼

NinjaSkillCFG.xml   <id>11004851</id> <normals>×3 <specials>×1 <skills>×N
        ▼
SkillCFG.xml        <name> / <cd> / <enterCd> / <mp> / <displayType> / <desc>
```

**槽位对照（实测能完整复现游戏内 tooltip）**

| 2 | 奥义 | 取 `specials` 首个，带 冷却 / 进场冷却 / 查克拉 |

**顺序**：奥义 → 普攻 → `NinjaSkillCFG.skills` 的**原始顺序**（不是按 id 排）。

**哪些不显示**：`SkillCFG` 的 `<showIcon>0</showIcon>` 不进浮窗（多为低阶/分身技能）。

技能描述里的 `<font color="#4dc831">` 要剥成纯文本。

**高亮词从哪来**

`<desc>` 里的彩色标记只有一种：`<font color="#4dc831">`（全表 29982 处，没有别的颜色）。
导出时把它和状态词表合起来标成 `【词】`：

| 来源 | 说明 |
| --- | --- |
| `<font color="#4dc831">…</font>` | 配置里写死的绿色词，如 `必中`、`打断`、`中毒`、`至少15连击时触发` |
| `config/skill/SkillExStateCFG.cfg` | 93 个状态名（倒地/浮空/麻痹/剧毒/封穴…），正文里出现就标 |

输出三个字段：`说明`（纯文本，保持原样）、`说明标记`（带 `【】`）、`高亮`（去重后的词序）。
`商城特惠.txt` 用 `说明标记`，并在段落开头标一行 `（【】= 游戏内高亮词）`。

> 游戏里橙色和绿色是两种颜色，但配置里只存了一种颜色值；橙色的那批（`打断`/`必中`）实际上也在 `<font>` 里，只是客户端按自己的配色表渲染。所以导出统一用 `【】`，不区分颜色。

实测：蝎[绯流琥] → 奥义「傀儡协同攻击」（冷却 3 / 进场 0 / 查克拉 20）、普攻「蝎尾攻击」、追打「毒千本攻击」、被动「傀儡召唤」「永恒的艺术」——与游戏内完全一致。

**限制**：图鉴里只收了一部分忍者形态。像 `佐井[泳装]`、`宇智波带土[忍界大战]` 这类较新的形态，item1/item2 里没有对应记录（各版本目录都试过），按名字查不到。

**查不到时怎么补**

悬停商品卡片时，客户端会去取两张图：

```
assets/battle/role/head_176_68/<忍者ID>.png     ← 忍者头像
assets/skill/40/<技能ID>.png                   ← 每个技能一个图标
```

这两个 ID 是直接暴露的：拿 `<忍者ID>` 去 `NinjaSkillCFG.xml` 一查就知道是哪个忍者的技能组，`<技能ID>` 的千位段也能对上（如 `2100565x` ↔ 忍者 `11005651`）。

实测这样补出来的两条：

| 碎片 | 忍者 ID | 依据 |
| --- | --- | --- |
| 20400387 佐井[泳装] | 11005651 | 请求了 `head_176_68/11005651.png` + `skill/40/2100565x.png` |
| 20400372 宇智波带土[忍界大战] | 11006041 | 请求了 `head_176_68/11006041.png` + `skill/40/2100604x.png` |

补出来的对应关系存在 `%APPDATA%\naruto-online-launcher\shop-ninja-map.json`（`{ "碎片物品ID": 忍者ID }`），也可以在代码里的 `NINJA_ID_SEED` 提供内置种子；两者同时存在时以 json 为准。

**自动兜底（每天开新商品也适用）**

导出时如果名字查不到，会自动：

1. 从本次抓包里取出所有忍者头像 ID（`head_176_68/<忍者ID>.png`），减掉已经用掉的；
2. 对每个未解析的碎片，数它的基础名（如「面麻」）在候选忍者**技能描述**里出现的次数，最高且明显领先的直接采用；
3. 剩下的做 1:1 排除（只剩一个碎片 + 一个候选就直接对上）；
4. 结果写进 `shop-ninja-map.json`，并在 `导出诊断.txt` 里留一行「自动推断：…」。

实例：`20400481 面麻[忍者之路] → 11016521`（技能描述里出现「面麻」6 次）、`20400460 宇智波斑[红夜之刃] → 11006091`（排除法）。

**配置目录按文件定位**

资源目录是逐个资源版本化的，同一个会话里 `CommonItemCFG` 可能在 `NarutoBeta11.37Build301`，而 `SkillExStateCFG` 在 `NarutoBeta11.30Build301`。导出时会扫一遍 `http-*.jsonl`，记下每个 `config/...` 文件实际用的是哪个目录，取数时**优先用这个目录**，避免「只试前 8 个目录」漏掉。

**没有收录的物品**

像 `22410037` 这种新道具，`CommonItemCFG.xml`、图鉴、掉落表里都查不到，导出时会空着名称/说明，并列进 `导出诊断.txt` 的「没有名称/说明的物品 ID」，等游戏补齐配置后自然就有了。

**通灵兽碎片（224xxxxx）**

`224` 开头的是通灵兽碎片，物品表和图鉴里都没有，单独一张表：

```
config/throughTheBeast/SummonBeastFragmentCFG.cfg
  记录头 0x11 + 碎片物品ID
  内容：[类型int] [名称「通灵兽·梦貘」] [招募所需碎片数 80] … [触发描述]
```

- 名称去掉「通灵兽·」前缀再加「碎片」→ `梦貘碎片`（与游戏浮窗标题一致）
- 描述就是浮窗里「10连击及以上时触发…」那段（配置里带 `<font>` 高亮）
- 数字 80 就是「收集80个碎片可招募」

注意：**这张表的 varint 是大端的**（`82 01` = 257），和别处的小端 LEB128 相反，长度仍然是 `值 >> 1`。

**上阵忍者属性加成**

浮窗下方「生命 30 / 攻击 15 / 防御 12 / 忍术 15」来自 `config/throughTheBeast/SummonMonsterCFG.cfg`：

- 记录键 = 碎片物品ID − 2410000（`22410037` → `20000037`）
- 表头字段顺序：`achievedWay, baseDefense, keyWord2, skillName, keyWord1, …, name, baseLife, baseNinjaAttack, …`
- 取法（实测与浮窗一致）：
  - **防御** = 记录头后第一个 `04 xx`（baseDefense）
  - **生命 / 忍术** = 短名（`梦貘`）后面紧挨的两个 `04 xx`（baseLife / baseNinjaAttack）
  - **攻击** = 记录里最后一个 `04 xx`（baseAttack）

**碎片名要补「碎片」两个字**

图鉴（`item3.pkg`）里的碎片名是 `面麻[忍者之路]`、`宇智波斑[红夜之刃]`，**不带「碎片」**；游戏浮窗显示的是 `面麻[忍者之路]碎片`。
所以导出时对 `204xxxxx` 的物品会统一补后缀：名字里没有「碎片」就加上。本地缓存 `shop-item-names.json` 里同样按这个规则存，旧数据下次导出会自动补上。

**为什么鼠标一放上去就能显示**

工具提示的文字**不是**悬停时才去服务器拿的——客户端启动时就把 `CommonItemCFG` / `NinjaSkillCFG` / `SkillCFG` / `archives/*.pkg` 全部拉下来了，悬停只是拿本地数据拼文本。悬停时唯一会发的网络请求是上面那两类**图片**（头像、技能图标）。所以在抓包里翻「悬停那一刻新增的图片请求」，就等于拿到了物品→忍者/技能的 ID。

**版本目录从哪来**

`res.huoying.qq.com/<NarutoBetaX.XXBuildNNN>/...` 的目录逐个资源版本化。取法：扫本会话 `http-*.jsonl`，把出现过的目录按「装 `config/bag/conf/CommonItemCFG.cfg` 的 → `entry.swf` 的 → 其它」排优先级，依次试到 200 为止。

**配置缓存**

上面几张表加起来首次要下 7 MB 左右（解压后约 40 MB），所以导出时会把**解压后的内容**缓存到 `%APPDATA%\naruto-online-launcher\cfg-cache\<url 的 sha1 前16位>.bin`。第二次导出基本零下载；版本更新后 URL 变了会自动换 key，不会读到旧数据。

**已知限制**

- 图标不能按 ID 拼 URL（资源目录逐个版本化），所以没滚到的卡片会缺图；
- 图鉴里的碎片名不带「碎片」两个字（`蝎[绯流琥]`），商城显示的是 `蝎[绯流琥]碎片`，所以人工核对过的本地缓存优先于图鉴名；
- 图鉴不含全部忍者形态，查不到技能时留空（见 15.3）；
- 时区固定按 UTC+8 算，不看本机设置。
